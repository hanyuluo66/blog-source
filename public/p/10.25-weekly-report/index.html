10.25 学习周报

周期：2026-10-19 ～ 2026-10-25

本周和以往不太一样，不是纯粹啃语法，而是一个完整项目落地 + 两块 C++ 专题。项目是「落小鱼」微信 AI 自动回复机器人，从一堆零散想法做到 v1.0.0 可用版本；专题是动态数组和高精度计算，配套刷掉了洛谷 P1009。

三条线其实互相咬合：项目里大量用到动态数据结构，高精度那套"用容器装大数"的思路和 vector 的用法是同一件事。

一、落小鱼：微信 AI 自动回复机器人 v1.0.0

仓库：https://github.com/hanyuluo66/luoxiaoyu

本周结论：v1.0.0 主体完成并可用，核心难点（隔离运行、识图、表情包）全部打通，剩余风险集中在微信登录与网络环境。

1.1 项目要解决什么

想让机器人自动回微信消息，最朴素的做法是模拟点击：找到窗口、读取控件文字、往输入框写字、点发送。这条路在微信 4.x 上会撞上三个死结：

  • 抢鼠标：机器人干活的时候，你自己没法用电脑
  • 读不到内容：微信 4.x 的会话列表是自绘的，UIA（Windows 辅助功能接口）只能读到几个导航按钮，拿不到消息列表
  • 不能后台：窗口最小化或被遮挡时，很多操作直接失效

所以最终方案是：把微信整个挪到一个独立的桌面会话里跑，主桌面完全不受影响。

1.2 最大难点：桌面分身隔离

Windows 有个叫 Child Session（RDP 子会话） 的机制，可以开出一个拥有独立输入队列的子桌面。微信和机器人在里面运行，主桌面该打字打字、该全屏游戏全屏游戏、该拖窗口拖窗口，互不干扰。

这一步踩的坑最多：

问题根因解决方式
启动后弹「你的凭据不工作」RDP 子会话要密码；账户是 Microsoft 账户且系统开着「仅允许 Hello 登录」关掉 Hello 独占 + 凭据存凭据管理器 + 账户拆成「域 + 用户名」两段（整串会被判为错误密码）
45 秒强制重连把人踢出去引擎在用户输密码时断线重连改为 20 秒显示窗口、90 秒提示、300 秒才重连
机器人所有发送超时分身里微信停在「进入微信」确认页，UIA 读不到聊天控件启动时和每次发送前自动点掉确认按钮
抢鼠标分身窗口可见时 RDP 把远端光标映射到本机指针任何鼠标/键盘动作前强制 hide_viewer()

配套的三个优化：

  • 分身登录体检：检查 hello_only（Hello 独占）状态、凭据是否已存、连续失败计数
  • 分身瘦身：登录后自动清掉 Steam / QQ / 网盘 / 驱动托盘等无关启动项，实测进程数 40 → 31
  • 干净启动：建分身之前临时挂起用户启动项，登录完成后立刻恢复。主桌面不受影响，即使中途失败也会回滚

1.3 消息收发：绕开界面直接读库

收消息没有走"读窗口文字"这条路，而是解密读取微信 4.x 的本地数据库。不点界面、不轮询窗口，稳定性和速度都好得多。

发消息分两类：

  • 文字：UIA 控件写文字 + 回车
  • 图片/表情包：走剪贴板。静态图用 SetImage，GIF 走 CF_HDROP 格式——这样能保留动画，直接贴图会把 GIF 变成第一帧静态图

切会话是另一个难点。微信 4.x 会话列表自绘，UIA 拿不到列表项；试过 ValuePattern 给搜索框写值，结果不触发搜索。最终改成真实键盘输入（SendInput）+ 逐行试点列表。

这里踩过一个隐蔽的坑：

收图永远失败 — 用了「消息行」的 local_id 去查，结果查到的是文字消息。改成用图片表自己的 local_id，并按 sort_seq 对齐，才正常。

群聊支持三种触发模式：仅 @我 / 关键词 / 全部消息，配黑白名单、免打扰、频率限制、人工接管、会话冷却。

1.4 识图与表情包

识图：微信 4.x 的图片是 wxgf（HEVC）容器，一般图像库读不了。用内置的 imageio-ffmpeg 转成标准 jpg，再交给视觉模型。

一个意外收获：实测 deepseek-chat 已经支持读图，不用另外买视觉 API。顺手加了 POST /api/vision/describe 单张图片测试接口，方便调试。

表情包：

  • 自动收藏别人发的表情包，用内容哈希去重，控制台有缩略图网格
  • 模型通过 [[表情]] 指令主动发；只写标记时只发表情、不发空文本
  • 拒绝兜底：用户要表情包而模型说"发不了"时，丢掉拒绝文字直接发一张

这个兜底是被逼出来的：

模型坚称"发不了表情包" — 根因是人设里写着"发不了图片"，而且对话历史里它自己说过"发不了"，于是不断自我强化。解决办法是四管齐下：改默认人设 + 自动迁移已存配置 + 过滤历史里的旧拒绝 + 流水线兜底。

教训：给大模型写人设时，别写它做不到的事；一旦它说过一次"我不行"，这句话会留在上下文里持续污染后续回答。

1.5 控制台与安全加固

控制台做了 9 个页面：概览 / 私聊 / 群聊 / 规则 / 人设 / AI 接口 / 节奏 / 日志 / 系统设置。用 Edge 的 --app 模式开独立窗口，不再占用浏览器标签页。配启动进度窗、页面进度条、托盘图标和看门狗。

安全这块是认真做过的：

  • 只监听 127.0.0.1，加 Host / Origin 校验，挡 DNS rebinding 与 CSRF
  • API Key 不回传前端：打码显示 + 留空保存表示不修改
  • 凭据改走 Windows 凭据管理器（CredWrite），不再出现在 cmdkey 命令行里（命令行参数任何本地进程都能看到，等于明文泄露）
  • 静态审计结果：shell=True / os.system / eval 零处，裸 except 零处，SQL 全参数化

1.7 本周其他两个值得记的问题

启动时黑窗口一闪：子进程（whoami / powershell / ffmpeg）各自开控制台。修法是加全局 Popen 子类守卫 + 所有调用走隐藏 spawn。

结果这个修法自己又炸了一次：

asyncio 导入崩溃 — 全局守卫把 Popen 换成了函数，而标准库里 asyncio 写的是 class Popen(Popen)（继承同名类），于是直接崩。改成子类实现就好了。

教训：monkey patch 标准库的东西时，必须先确认它有没有被继承。换成函数会破坏继承链，这种 bug 报错信息还特别绕。

模型接口连不上：系统代理开着但代理程序没运行，httpx 默认走系统代理，于是请求全挂。改成默认直连，需要代理时在控制台勾选——显式优于隐式，别让库去猜系统配置。

1.8 遗留风险

  1. RDP 子会话连接偶发卡住（RDP=2 一直不连上）：Windows 家庭版 Child Session 的固有行为，已加"卡住重启引擎"自愈，极端情况需重启电脑
  2. 首次登录必须人工输一次密码：登录框在分身的独立桌面，键盘注入进不去
  3. 同一微信号不能两台电脑同时在线：分身登录后主桌面不要再登同一个号
  4. git 协议访问 github.com 被墙：本次推送改用 GitHub API 完成，后续大改动需代理
  5. 代码仓库未含 exe：release 产物 78 MB，不适合进仓库，需要时本地打包

二、C++ 动态数组

2.1 为什么需要动态数组

C 语言里数组长度必须在编译期确定：

int n;
cin >> n;
int arr[n];   // C++ 标准不允许！这是 GCC 扩展（VLA）

问题在于：运行时才知道要多少空间的场景太常见了。读一个文件不知道有多少行、用户输入一个 n 不知道多大、容器里的元素数量一直在变。这时候必须用动态数组。

C++ 提供两条路：底层的 new[] / delete[]，和上层的 std::vector。

2.2 new[] 与 delete[]

#include <iostream>
using namespace std;

int main() {
    int n = 5;
    int* arr = new int[n];        // 在堆上申请 n 个 int

    for (int i = 0; i < n; i++) {
        arr[i] = i * i;           // 用法和普通数组完全一样
    }
    for (int i = 0; i < n; i++) {
        cout << arr[i] << " ";
    }
    cout << endl;                 // 输出：0 1 4 9 16

    delete[] arr;                 // 必须释放，否则内存泄漏
    arr = nullptr;                // 释放后置空，防止野指针

    return 0;
}

几个关键点：

  • new[] 配 delete[]，new 配 delete，不能混用。混用是未定义行为，可能崩可能不崩
  • 释放后置空：delete[] arr 之后 arr 还留着旧地址，成了野指针，再用就是未定义行为
  • 初始化为 0：new int[n]() 加个括号，全部置零；不加括号则是随机值
  • 申请失败会抛 std::bad_alloc，除非用 new (nothrow)

动态二维数组要两层循环申请、逆序两层释放：

int rows = 3, cols = 4;
int** mat = new int*[rows];
for (int i = 0; i < rows; i++) {
    mat[i] = new int[cols]();     // 加 () 置零
}

// 用完逆序释放：先释放每一行，再释放指针数组
for (int i = 0; i < rows; i++) {
    delete[] mat[i];
}
delete[] mat;
mat = nullptr;

释放顺序其实正序逆序都行，但必须先释放 mat[i] 再释放 mat。一旦 mat 被释放，就再也拿不到 mat[i] 的地址了，那 rows 块内存就永久泄漏。

2.3 三个必须避开的错误

// 错误1：忘记释放 —— 内存泄漏
int* p = new int[1000000];
// 函数结束，p 出栈，那 4MB 再也找不回来了

// 错误2：重复释放 —— 崩溃或未定义行为
delete[] p;
delete[] p;        // 第二次释放同一块内存

// 错误3：释放后继续用 —— 野指针
delete[] p;
p[0] = 1;          // 访问已释放内存，可能悄悄改坏别人的数据

第三个最阴险：它不一定立刻崩，可能过很久才在别处爆出来，排查成本极高。

2.4 vector：自动管理长度的动态数组

new[] 的所有痛点，std::vector 都解决了：自动扩容、自动释放、知道自己多长、能直接用范围 for。

#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> v;                 // 空 vector
    v.push_back(10);               // 尾部追加
    v.push_back(20);
    v.push_back(30);

    cout << "size=" << v.size() << endl;          // 3
    cout << "front=" << v.front() << endl;        // 10
    cout << "back=" << v.back() << endl;          // 30
    cout << "v[1]=" << v[1] << endl;              // 20

    v.pop_back();                                 // 删掉最后一个
    cout << "after pop, size=" << v.size() << endl;  // 2

    // 三种遍历方式
    for (int i = 0; i < (int)v.size(); i++) cout << v[i] << " ";
    cout << endl;

    for (int x : v) cout << x << " ";             // 范围 for（C++11）
    cout << endl;

    for (auto it = v.begin(); it != v.end(); ++it) cout << *it << " ";
    cout << endl;

    return 0;
}

常用操作速查：

操作作用
push_back(x)尾部追加
pop_back()删除尾部元素
insert(it, x)在迭代器位置插入
erase(it)删除迭代器位置元素
size() / empty()长度 / 是否为空
clear()清空
resize(n)改变元素个数
reserve(n)预留容量，不改变 size

2.5 扩容机制（实测数据）

size() 是实际元素个数，capacity() 是已申请的空间能装多少个。push_back 在 size == capacity 时会触发扩容：申请一块更大的内存、把旧元素全部搬过去、释放旧内存。

下面是本机 g++ 实测的扩容轨迹：

vector<int> v;
size_t lastCap = 0;
for (int i = 1; i <= 40; i++) {
    v.push_back(i);
    if (v.capacity() != lastCap) {
        cout << "push " << i << " -> size=" << v.size()
             << " capacity=" << v.capacity() << endl;
        lastCap = v.capacity();
    }
}

实际输出：

push 1  -> size=1   capacity=1
push 2  -> size=2   capacity=2
push 3  -> size=3   capacity=4
push 5  -> size=5   capacity=8
push 9  -> size=9   capacity=16
push 17 -> size=17  capacity=32
push 33 -> size=33  capacity=64

规律很清楚：容量按 1、2、4、8、16、32、64 翻倍增长。

为什么是翻倍而不是每次 +1？算一笔账就明白了：

  • 每次 +1：插 n 个元素，搬运次数是 $1+2+3+\dots+n = \frac{n(n+1)}{2}$，均摊每次 $O(n)$
  • 翻倍：搬运次数是 $1+2+4+8+\dots \approx 2n$，均摊每次 $O(1)$

所以 push_back 的均摊时间复杂度是 O(1)，虽然单次可能很慢。

扩容标准没有强制规定倍数，libstdc++（GCC）和 MSVC 都是 2 倍，有些实现用 1.5 倍。别写依赖具体倍数的代码。

2.6 reserve：提前把空间开好

如果知道大概要放多少元素，用 reserve 一次性开好，避免中途反复扩容搬运：

vector<int> r;
r.reserve(100);
cout << "after reserve(100): size=" << r.size()
     << " capacity=" << r.capacity() << endl;

for (int i = 0; i < 100; i++) r.push_back(i);
cout << "after 100 push: size=" << r.size()
     << " capacity=" << r.capacity() << endl;

实测输出：

after reserve(100): size=0   capacity=100
after 100 push:     size=100 capacity=100

对比不加 reserve 的话，这 100 次 push 会触发 7 次扩容。reserve 只改 capacity，不改 size——这点很容易搞混，所以此时 r[0] 还是非法访问。

另一个必须知道的坑：扩容会搬家，意味着扩容前拿到的迭代器和指针全部失效。

vector<int> v = {1, 2, 3};
int* p = &v[0];        // 指向第一个元素
for (int i = 0; i < 100; i++) v.push_back(i);  // 触发扩容搬家
cout << *p;            // 未定义行为！p 指向的内存已经被释放了

这类 bug 在小数据量下测不出来，一上量就随机崩。

2.7 new[] 与 vector 对照

维度new[] / delete[]std::vector
长度可变不可，需手动重新申请+拷贝自动扩容
释放手动 delete[]，忘了就泄漏出作用域自动释放（RAII）
知道自己多长不知道，得另外存个变量size() 随时可查
越界检查无at() 有，[] 无
遍历只能下标或指针下标 / 迭代器 / 范围 for
适用场景需要极致控制、和 C 接口交互绝大多数情况

结论：日常写 C++ 一律用 vector，只有对接 C 库或者需要精确控制内存布局时才用 new[]。

顺带说一句，这周的 P1009 高精度就是用 vector<int> 存每一位数字——动态数组和高精度天然是配套的，因为大数有多少位事先并不知道。

2.8 关键要点

  • new[] 必须配 delete[]，释放后立刻置 nullptr
  • 二维动态数组必须先释放每一行、再释放指针数组，顺序反了就泄漏
  • vector 的 size 是元素个数，capacity 是空间容量，两者不相等
  • push_back 均摊 O(1)，靠的是翻倍扩容；扩容会让所有迭代器和指针失效
  • 已知规模就用 reserve 预留，避免反复搬家
  • v.size() 返回的是无符号类型 size_t，写 for (int i = 0; i < v.size() - 1; i++) 在空 vector 上会因为下溢变成巨大正数，导致越界。要么转成 (int)v.size()，要么单独判空

三、高精度计算与洛谷 P1009

3.1 题目

P1009 [NOIP1998 普及组] 阶乘之和

用高精度计算出 $S = 1! + 2! + 3! + \cdots + n!$（$n \le 50$）。

其中 ! 表示阶乘，定义为 $n! = n \times (n-1) \times (n-2) \times \cdots \times 1$。例如 $5! = 5 \times 4 \times 3 \times 2 \times 1 = 120$。

输入格式：一个正整数 $n$ 输出格式：一个正整数 $S$

样例：输入 3，输出 9（因为 $1!+2!+3! = 1+2+6 = 9$）

数据范围：对于 100% 的数据，$1 \le n \le 50$

题目里"用高精度计算“这几个字是明示：常规类型装不下。

3.2 为什么必须高精度（实测溢出边界）

先看 C++ 各种整数类型的上限：

类型字节最大值十进制位数
int4214748364710 位
long long8922337203685477580719 位
unsigned long long81844674407370955161520 位

而 $50!$ 是多少位？65 位。差了三倍还多，连 unsigned long long 都装不下，更别提题目要的是 $1!$ 到 $50!$ 累加。

我写了个程序实测溢出发生在哪一步：

#include <iostream>
#include <climits>
using namespace std;

int main() {
    unsigned long long f = 1;
    int firstBad = -1;
    for (int i = 1; i <= 25; i++) {
        // 关键：在相乘之前判断，f*i 会不会溢出
        bool willOverflow = (f > ULLONG_MAX / (unsigned long long)i);
        f *= (unsigned long long)i;
        if (willOverflow && firstBad < 0) firstBad = i;
        if (i >= 18) {
            cout << i << "! = " << f;
            if (willOverflow) cout << "   <== OVERFLOW, WRONG";
            else cout << "   ok";
            cout << endl;
        }
    }
    cout << "first overflow at: " << firstBad << "!" << endl;
    return 0;
}

实测输出：

18! = 6402373705728000        ok
19! = 121645100408832000      ok
20! = 2432902008176640000     ok
21! = 14197454024290336768    <== OVERFLOW, WRONG
22! = 17196083355034583040    <== OVERFLOW, WRONG
...
first overflow at: 21!

结论：20! 是 unsigned long long 能装下的最大阶乘，21! 开始溢出。

这里有个特别值得注意的现象。21! 的真实值是：

51090942171709440000   （20 位）

程序算出来的是：

14197454024290336768

两个数都是 20 位，位数看起来完全正常，肉眼根本发现不了错。而它俩的关系是：

$$51090942171709440000 \bmod 2^{64} = 14197454024290336768$$

溢出就是静默取模。不报错、不崩溃、不警告，位数还挺合理，只是数值悄悄错了。这是溢出最可怕的地方——如果你只用 $n \le 20$ 的数据测，程序完全正常，一交到 $n = 21$ 就全错，而且错得毫无征兆。

想提前发现溢出，判断方式不是"乘完之后看结果对不对”，而是乘之前问一句：f > ULLONG_MAX / i 吗？如果成立，这一步必溢出。

3.3 高精度的核心思路

既然一个变量装不下，那就用容器把每一位数字分开存。

以 $50!$ 为例，它有 65 位，就用一个 vector<int> 存 65 个元素，每个元素存一位（0~9）：

vector<int> A;   // A[0] 存个位，A[1] 存十位，A[2] 存百位……

注意是低位在前（倒序存储）。为什么？因为加法和乘法都是从低位往高位算并进位的，倒序存的时候：

  • 低位在 A[0]，从头开始遍历，天然对应竖式计算的顺序
  • 进位产生了新的高位，直接 push_back 追加到尾部就行

如果是正序存（高位在前），每次进位扩位都要在头部插入，而 vector 头部插入要把所有元素后移一位，代价 $O(n)$。倒序存储把这个开销降到 $O(1)$。

输出时反过来，从最后一个元素往前打印。

3.4 高精度乘低精度

这是本题的核心。计算 $i!$ 时用 $(i-1)! \times i$，一个大数乘一个小整数，模拟竖式：

vector<int> mul(const vector<int>& A, int b) {
    vector<int> C;
    int carry = 0;                       // 进位
    for (int i = 0; i < (int)A.size() || carry; i++) {
        if (i < (int)A.size()) carry += A[i] * b;
        C.push_back(carry % 10);         // 当前位留下个位数
        carry /= 10;                     // 剩下的进位
    }
    return C;
}

逐行拆解：

  • carry 同时承担两个角色：当前的进位和累加中间值
  • 循环条件 i < A.size() || carry：位数走完了但进位还没处理完时，要继续循环把高位补出来。这一条最容易漏——比如 $999 \times 9$，三位乘完还有进位要变成第四位
  • carry % 10 取当前位，carry / 10 留给下一位

3.5 高精度加法

vector<int> add(const vector<int>& A, const vector<int>& B) {
    vector<int> C;
    int carry = 0;
    for (int i = 0; i < (int)max(A.size(), B.size()) || carry; i++) {
        if (i < (int)A.size()) carry += A[i];
        if (i < (int)B.size()) carry += B[i];
        C.push_back(carry % 10);
        carry /= 10;
    }
    return C;
}

和乘法结构完全一致，只是把 A[i] * b 换成 A[i] + B[i]。

i < A.size() 和 i < B.size() 两个判断是必须的——两数长度不等时，短的那个已经没位了，不能再读，否则越界。

3.6 完整代码

这份代码我实际编译运行过，四个测试点全部通过（含洛谷官方样例）：

#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

// 高精度 × 低精度
vector<int> mul(const vector<int>& A, int b) {
    vector<int> C;
    int carry = 0;
    for (int i = 0; i < (int)A.size() || carry; i++) {
        if (i < (int)A.size()) carry += A[i] * b;
        C.push_back(carry % 10);
        carry /= 10;
    }
    return C;
}

// 高精度 + 高精度
vector<int> add(const vector<int>& A, const vector<int>& B) {
    vector<int> C;
    int carry = 0;
    for (int i = 0; i < (int)max(A.size(), B.size()) || carry; i++) {
        if (i < (int)A.size()) carry += A[i];
        if (i < (int)B.size()) carry += B[i];
        C.push_back(carry % 10);
        carry /= 10;
    }
    return C;
}

int main() {
    int n;
    cin >> n;

    vector<int> fact = {1};   // fact = i!，从 0! = 1 开始
    vector<int> sum  = {0};   // sum  = 累加结果

    for (int i = 1; i <= n; i++) {
        fact = mul(fact, i);       // i! = (i-1)! × i
        sum  = add(sum, fact);     // S += i!
    }

    // 倒序存储，所以要从高位往低位打印
    for (int i = (int)sum.size() - 1; i >= 0; i--) cout << sum[i];
    cout << endl;

    return 0;
}

思路要点：

  1. 阶乘递推：$i! = (i-1)! \times i$，不必每次从头乘，总复杂度从 $O(n^2)$ 降到 $O(n)$ 次大数乘法
  2. 初始化 fact = {1}：对应 $0! = 1$，循环从 $i=1$ 开始乘就得到 $1!$。这一步如果写成 {0}，后面全是 0
  3. 初始化 sum = {0}：累加的中性元
  4. 两个辅助函数职责单一：mul 只管乘、add 只管加，主循环非常干净

验证方法：我用 Python 的 math.factorial 独立算了一遍 $S(50)$，得到完全相同的 65 位数。Python 的整数是任意精度的，天然适合当高精度算法的对拍工具。

这个习惯值得保持：手写的高精度算法一定要有独立实现对拍。因为溢出是静默的，错一位你完全看不出来，只有对拍能发现。

3.8 手算验证前几步

用 $n = 3$ 走一遍，确认逻辑正确：

初始：fact = [1]  (即 1，倒序存)，sum = [0]

i=1: fact = mul([1], 1) = [1]        → 1! = 1
     sum  = add([0], [1]) = [1]      → S = 1

i=2: fact = mul([1], 2) = [2]        → 2! = 2
     sum  = add([1], [2]) = [3]      → S = 1+2 = 3

i=3: fact = mul([2], 3) = [6]        → 3! = 6
     sum  = add([3], [6]) = [9]      → S = 3+6 = 9

输出：从高位到低位打印 [9] → 9  ✓

再看一个会产生进位的，$n = 5$ 的最后一步：

i=4: fact = 4! = 24，倒序存为 [4, 2]
i=5: fact = mul([4,2], 5):
       i=0: carry = 4*5 = 20  → push 20%10=0, carry=2
       i=1: carry = 2 + 2*5 = 12 → push 12%10=2, carry=1
       i=2: A 已走完但 carry=1 → push 1%10=1, carry=0
     fact = [0, 2, 1]  → 倒着读是 120  ✓ (5! = 120)

第三步 i=2 就是 3.4 节里说的"位数走完但进位没处理完"，|| carry 这个条件在这里起了作用。如果漏掉它，5! 会算成 20 而不是 120。

3.9 复杂度与进一步优化

时间复杂度：$n$ 轮，每轮一次高精度乘法 + 一次高精度加法。$i!$ 约有 $O(i \log i)$ 位，所以总复杂度约 $O(n^2 \log n)$。$n \le 50$ 时最多几十位数，远在 1 秒时限内。

空间复杂度：$O(n \log n)$，存两个大数。

可以进一步优化的方向（还没实现，记下来）：

  • 压位：一个数组元素不只存 1 位，而是存 4 位或 9 位（相当于把十进制换成 $10^4$ 进制）。这样 65 位数字只需 17 个元素，运算次数降到 1/4。代价是输出时要补前导零，printf("%04d", x)
  • 本题 $n \le 50$ 规模很小，压位收益不明显；但如果是 P1591 那种要处理 $n!$ 数位的题，压位就很划算

3.10 关键要点

  • 看到"用高精度计算“或者数据范围超过 $10^{18}$，直接放弃常规类型
  • 溢出是静默取模，不报错、位数还可能正常，必须主动检查
  • 检查溢出的正确姿势是乘之前判断 a > MAX / b，不是乘完之后看结果
  • 高精度用倒序存储（低位在前），这样进位扩位是 push_back，$O(1)$
  • 循环条件一定要带 || carry，否则最高位进位会丢
  • 两数相加时要分别判断 i < A.size() 和 i < B.size()，长度不等时短的那个不能越界读
  • 输出记得倒着打印
  • 写完一定要找独立实现对拍，Python 的任意精度整数是最好用的对拍工具

三点收获

1. 项目里最难的部分往往不在算法，而在环境

这周花在"让微信在子会话里正常登录"上的时间，比写业务逻辑还多。凭据格式、Hello 独占、重连时机、确认页遮挡——每一个都不是技术难题，但每一个都能让整条链路断掉。

体会是：遇到讲不通的失败，先怀疑环境状态，别急着改业务代码。“凭据不工作"这个问题如果一直在密码对不对上打转，永远找不到根因（真实原因是账户串需要拆成域和用户名两段）。

2. 静默错误比崩溃可怕得多

这周遇到两个静默错误：整数溢出（位数正常、数值全错）和模型自我强化"我发不了图片”（行为正常、结果不对）。两个都不报错，都是靠对拍和实际测试才发现的。

由此养成一个习惯：关键计算必须有独立验证手段。高精度题用 Python 对拍，项目功能用实际消息测试，别相信"看起来对"。

3. 动态数组是本周两块知识的连接点

原本以为 vector 和 P1009 是两件事，写完发现是同一件：高精度的本质就是用一个能自动增长的容器存位数未知的大数。push_back 处理进位扩位、size() 随时知道当前多少位、出作用域自动释放——vector 的每个特性在高精度里都用上了。

这也是为什么 2.5 节要认真研究扩容机制：如果 push_back 是 $O(n)$ 的，高精度乘法就不可能是现在这个复杂度。
