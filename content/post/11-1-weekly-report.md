## 一、小鲸鱼：QQ 端 AI 陪伴机器人

### 1.1 为什么要两个进程

一开始想一个程序搞定，最后发现职责天然分两层：

| 层 | 组件 | 职责 |
| --- | --- | --- |
| 协议层 | SnowLuma | 登 QQ、收发消息、跟腾讯的私有协议打交道 |
| 应用层 | AstrBot | 对话、插件、人设、工具调用 |

中间用 **OneBot v11** 连起来：SnowLuma 作为 WS 客户端主动连 AstrBot 的 `ws://127.0.0.1:6199/ws`（**反向 WS**），所以 AstrBot 不需要知道 QQ 密码，SnowLuma 也不需要懂大模型。

这个分层带来一个很实际的收益：**换协议端不影响应用层**。后面接微信也是同样的思路。

### 1.2 OneBot 的三个概念

**① 反向 WS**：不是客户端连服务端，而是协议端（管 QQ 的那个）去连应用端。好处是应用端不用暴露公网、不用管重连鉴权，协议端自己带 `reconnectIntervalMs` 重连。

**② 事件（event）**：所有消息、通知、请求都是事件，统一是 JSON。`post_type` 决定大类：

```
post_type = message  → 收到消息
post_type = notice   → 群戳、撤回、表情回应
post_type = request  → 好友申请、加群申请
```

**③ flag**：请求类事件里带的一个凭据，**同意/拒绝好友申请必须用它，而且不可回查**——事件过去就没了，查不到。

第三条是这周踩得最深的一个坑（见 1.7）。

### 1.3 记忆库：让三个客户端共用一个大脑

微信端、QQ 端、电脑端（DSH）三个地方都在跟我说话，但它们各自的历史是隔离的。目标是：**不管从哪个入口进来，都记得同一件事**。

最终做成一个本地服务（`127.0.0.1:8940`），四个来源统一入库：

| 来源 | 条数 | 说明 |
| --- | --- | --- |
| 微信 | 285 | 从本地数据库解密读出来的真实聊天记录 |
| QQ | 221 | 插件在对话时实时写入 |
| 日记 | 19 | 每天蒸馏出的"重要的事" |
| 电脑端（DSH） | 22 | 桥接服务定时把会话摘要写进来 |
| 手动 | 1 | 我自己手动录的 |
| **合计** | **548** | 1024 维 |

**检索没有用神经网络嵌入**，原因很实在：

- DeepSeek 网关只有 `deepseek-flash` / `deepseek-v4-pro` 两个模型，**没有 `/embeddings` 接口**
- 本地跑神经网络嵌入模型（几百 MB + 推理开销）对一台家用电脑太重

所以用了**哈希嵌入 + 混合打分**的简化方案：

```
分词：jieba 切词 + 字符 bigram
向量：每个 token 做 blake2b → 映射到 1024 维 → 累加（L2 归一化）

得分 = 0.60 × 词语包含度
     + 0.30 × 余弦相似度
     + 0.10 × 时间新近度
```

**这个方案的诚实评价**：

- 优点：零依赖、可复现、毫秒级、完全离线
- 缺点：**语义能力很弱**。"要不要吃饭"和"饿不饿"在哈希空间里几乎无关，只有字面重合才抓得到

它的定位不是"理解"，而是"**把相关的那几条找出来交给大模型**"。真正做语义的是后面那一次大模型调用。

### 1.4 电脑控制：三个"看起来成功其实没做"

让我接管电脑（截图、点鼠标、打字）的过程中，连续遇到三次同类问题：**接口返回成功，但实际什么都没发生**。

**① 截图截不全**

现象：截出来的图只有 1707×1067，但屏幕明明是 2560×1600。

根因：进程**不是 DPI 感知的**。Windows 在 150% 缩放下会对非 DPI 感知进程谎报逻辑分辨率：

```
2560 × 1600  ÷  1.5  ≈  1707 × 1067   ← 正好就是截到的那块
```

解决：启动时声明 DPI 感知，然后按 `SystemInformation.VirtualScreen` 取真实边界。

```python
ctypes.windll.shcore.SetProcessDpiAwareness(2)   # Win8.1+
```

**② 键盘注入"成功"但一个字都没打进去**

现象：`SendKeys("hello")` 返回成功，目标窗口里什么都没有。

根因：`SendKeys` 是老 API，在后台进程 + 非前台窗口的情况下会静默失败。

解决：改用 `SendInput`，并且**用 `KEYEVENTF_UNICODE` 逐字符注入**（绕开键盘布局差异）：

```python
# 每个字符发一对 down/up，走 unicode 通道
inp.ki.wVk = 0
inp.ki.wScan = ord(ch)
inp.ki.dwFlags = KEYEVENTF_UNICODE
```

验证方式也不是"看返回码"，而是**真去检查结果**：让 cmd 窗口里写一个 `inject_proof.txt`，读回来确认内容；再用 CapsLock 状态做 0→1→0 探针。

**③ 窗口切不到前台**

现象：`SetForegroundWindow` 调用成功，窗口没有激活。

根因：Windows 的**前台锁**——只有当前拥有前台的进程才能把前台交给别人，后台进程调用会被系统忽略。

解决：先模拟一次 Alt 键（系统会认为"用户有操作意图"，临时解锁），再调 `SetForegroundWindow`，失败则退到 `BringWindowToTop` + 最小化/还原组合。

### 1.5 主动聊天：15 分钟的静默期

需求是"她每隔 30~60 分钟自己找我说话"。配置改了，但行为没变。

读源码才看明白调度节奏：

```python
async def _proactive_loop(self):
    await asyncio.sleep(900)      # ① 启动后先睡 15 分钟
    while True:
        await self._proactive_tick()
        await asyncio.sleep(420)  # ② 之后每 7 分钟才判定一次
```

两个数字一起拖慢：**每次重启后 15 分钟内绝对不会发**，之后判定精度也只有 7 分钟。

改完：

| 位置 | 改前 | 改后 |
| --- | --- | --- |
| 启动预热 | 900 秒 | **60 秒** |
| 判定周期 | 420 秒 | **120 秒** |

间隔本身是 `random.uniform(min_hours, max_hours) * 3600`，没有隐藏下限，所以配置 `0.5 / 1.0` 就能拿到"一小时 1~2 次"。

**验证方式**：不看日志猜，直接读它的状态文件，算 `next - last`：

```
last_sent = 19:32:19
next      = 20:11:08     → 间隔 39 分钟  ✓
```

**顺带发现一个更隐蔽的问题**：`next_proactive_ts` 停在当天 00:49 一直没被更新，说明那个调度任务根本没在跑。最后定位到是容器反复重启（24 小时内 12 次），每次重启都会重新开始一个 15 分钟的预热期——**重启频率高于预热时长时，这个循环永远不会执行到第二次**。这就是为什么"配置没错、代码没错、就是不干活"。

### 1.6 说出来是一回事，想不想说又是另一回事

主动聊天有了，QQ 空间说说也做了。第一版是**定时驱动**：每天 2 条，10:00–23:00。

跑出来问题很明显——**平静的日子也得硬凑内容**，写出来的东西干巴。

所以推翻重做，改成**心情驱动**：每隔 35~70 分钟问她一次，一次调用同时产出"心情 + 强度 + 想不想发 + 正文"：

```json
{"mood": "有点不服又软", "intensity": 35, "want": true,
 "reason": "心绪不够", "text": "想发才写正文"}
```

三道闸门：

| 闸 | 条件 |
| --- | --- |
| 想不想 | `want == true`（她自己表态） |
| 心绪够不够 | `intensity >= 45` |
| 频率 | 距上条 ≥ 90 分钟、每天 ≤ 6 条 |

第一次实测就被闸住了：

```
posted: false
mood: "有点不服又软"
intensity: 35
reason: "心绪不够（35 < 45）"
```

**这个"没发"比"发了"更能说明设计对了**。定时驱动的产品逻辑是"到点必须产出"，心情驱动的逻辑是"没话说可以不说"。

### 1.7 白名单拦住的不是消息，是凭据

这是本周唯一需要动 AstrBot 核心的一处。

目标是：有人加好友时通知我，我说一句同意或拒绝。

**第一个问题：事件根本到不了插件。**

好友申请事件被适配器转成 `FRIEND_MESSAGE`，而它的**会话 ID 是申请人自己的 QQ**：

```
snowluma:FriendMessage:999888777   ← 陌生人的号
```

必然不在白名单（白名单只有我自己的会话）里，于是 `whitelist_check` 直接：

```python
event.stop_event()
```

插件收不到事件，也就拿不到 `flag`。

**第二个问题：flag 不可回查。**

OneBot 没有"列出待处理好友申请"这种接口（试探 `get_friend_add_request` 返回 `retcode 1404 unknown action`）。flag 只在事件里出现，**一旦丢了就永久无法同意或拒绝**。

所以只能让事件进来。补丁只有四行：

```python
# [qqbot-patch] request-exempt
raw_request = getattr(getattr(event, "message_obj", None), "raw_message", None)
if isinstance(raw_request, dict) and raw_request.get("post_type") == "request":
    return
```

**凭什么说它安全？** 因为申请事件 `message_str` 是空字符串、也没有图片或引用，而管道的 LLM 阶段有这么一段：

```python
has_valid_message = bool(event.message_str and event.message_str.strip())
if not has_provider_request and not has_valid_message and not has_media_content and not has_reply:
    logger.debug("skip llm request: empty message and no provider_request")
    return
```

也就是说：**放行只让插件看到，不触发任何自动回复**。这一点是读了源码确认的，不是猜的。

**实测（五步全过）**：

| 步 | 结果 |
| --- | --- |
| 模拟一条申请 | pending 里存下 flag 和留言，`stop_event=True` |
| 主人查看列表 | `1. 999888777（10-31 22:50）/ 留言：你好，我是隔壁班的…` |
| 陌生人查看 | `这个只有我爸能让我做。` |
| 发通知 | `私聊 2379871014 \| 发送：【好友申请】` |
| 同意（假 flag） | OneBot 报 `OIDB 316: one of uid/openid is invalid` |

最后一条特别值得记：**用假 flag 试出来的报错，反而证明了链路是通的**——它真的走到了协议层，只是凭据无效。如果这里返回 `retcode 0`，那才是坏消息（说明是假成功）。

> 遗留风险：这是改在核心文件里的，升级 AstrBot 会覆盖。已经留了 `.bak` 备份，补丁脚本带幂等 marker，升级后重跑一次即可。

## 二、C++ 二维数组与洛谷 P5728

### 2.1 题目

**P5728 【深基5.例5】旗鼓相当的对手**

> 现有 $N$ 名同学，每名同学有语文、数学、英语三科成绩。若两名同学的**各科成绩分差都不超过 5 分**，且**总分分差不超过 10 分**，则称二人"旗鼓相当"。求有多少对这样的同学。

输入第一行 $N$，接下来 $N$ 行每行三个整数（语、数、英）。$N \le 1000$。

### 2.2 我自己写的第一版：四个 bug

下面是我实际写出来的第一版（编译都过不了，但值得留着）：

```cpp
#include<bits/stdc++.h>
using namespace std;
int main()
{
    int n,s=0;
    int d[1005][3];
    int z[1005];
    cin>>n;
    for(int i=0;i<n;i++)
    {
        for(int j=0;j<3;j++)
        {
            cin>>d[i][j];
            z[i]+=d[i]d[j];        // ← ①
        }
    }
    for(int i=0;i<n;i++)
    {
        for(int j=0;j<n;j++)
        {
            if(abs(a[i][1]-a[j][1])<=5&&abs(a[i][2]-a[j][2])<=5
             &&abs(a[i][3]-a[j][3])<=5&&abs(z[i]-z[j])<=10) s++;   // ← ②③
        }
    }
    s-=n;                          // ← ④
    cout<<s;
    return 0;
}
```

四个问题：

| # | 问题 | 后果 |
| --- | --- | --- |
| ① | `d[i]d[j]` 少了 `[` | **编译期就报错**（唯一的好消息） |
| ② | `z[1005]` 没初始化 | 累加得到垃圾值，总分全错 |
| ③ | 数组名写成 `a`、下标用 `1/2/3` | 变量未定义 + **数组越界读**（第二维只有 `0..2`） |
| ④ | `j` 从 `0` 开始 | 每对被算两次，用 `s -= n` 硬补，逻辑上补不回来 |

①属于幸运——编译器直接拦住。②③④全是**编译通过、可能连样例都能过、但结果错**的类型。

### 2.3 数组不初始化就是垃圾

```cpp
int z[1005];       // 里面是栈上残留的垃圾值，不保证是 0
z[0] += 90;        // 结果 = 垃圾值 + 90
```

C++ 的局部数组（栈上）**不会自动清零**。而全局数组、`static` 数组会清零，这个区别很容易记混。

三种正确写法：

```cpp
int z[1005] = {0};                 // ① 全零（推荐）
int z[1005] = {};                  // ② C++11，等价
memset(z, 0, sizeof(z));           // ③ C 风格
```

> 这不是"习惯问题"，是**正确性问题**。同样的代码在小数据下可能恰好是 0（栈没被用过），一上量就崩，排查成本极高。

### 2.4 下标从 0 开始，这个真的会反复错

`int d[1005][3]` 的第二维合法下标是 **`0、1、2`**，没有 `3`。

```cpp
d[i][3]   // 越界！读到的是下一行的 d[i+1][0]
```

**为什么越界不一定崩？** 因为二维数组在内存里是**连续的一整块**：

```
d[i][0]  d[i][1]  d[i][2]  d[i+1][0]  d[i+1][1] ...
   0        1        2        3(越界)     4
```

`d[i][3]` 实际读到 `d[i+1][0]`，程序不崩、不报错，**读到的是别的同学的语文成绩**，结果完全不可解释。

这也是我用 `1/2/3` 当下标时最危险的地方：它不仅错，而且**错得安静**。

### 2.5 `abs`：差多少，不是减多少

判断"分差不超过 5"，直觉写 `a - b <= 5` 是错的：

```
A = 90, B = 70
A - B = 20   → 20 > 5   判为"差距大"
B - A = -20  → -20 <= 5 判为"差距小"   ← 同一个事实，两个结论
```

差值必须取绝对值：

```cpp
abs(chinese[i] - chinese[j]) <= 5
```

这一点我用两个版本对着跑验证过：同一组数据，"不用 abs" 版本答案比正确答案**大**（多算了反向差）。

### 2.6 `j = i + 1`：从源头消掉重复

要求的是"**有多少对**"，不是"有多少个有序组合"。

```cpp
for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++)      // 0..n-1：每对算两次
```

两组问题：

1. **自己和自己比**：`i == j` 时分差全是 0，必然成立 → 多算 `n` 次
2. **每对算两次**：(1,2) 和 (2,1) 各算一遍 → 结果翻倍

我当时的补法是 `s -= n`，只修了第 1 个，第 2 个还在。正确写法是从源头限制：

```cpp
for (int j = i + 1; j < n; j++)      // 每对只算一次
```

> 经验：**重复计数要修在循环条件上，不要修在结果上**。加减法补丁只能补你想到的那一种重复。

### 2.7 最终版本

考虑到基础还在打，最终版本用**四个一维数组**而不是二维数组（可读性优先）：

```cpp
#include <bits/stdc++.h>
using namespace std;

int main()
{
    int n;
    cin >> n;

    int chinese[1005], math[1005], english[1005], total[1005];

    // 第一步：把每个同学的成绩都存下来
    for (int i = 0; i < n; i++)
    {
        cin >> chinese[i] >> math[i] >> english[i];
        total[i] = chinese[i] + math[i] + english[i];
    }

    // 第二步：两两比较
    int ans = 0;
    for (int i = 0; i < n; i++)
    {
        for (int j = i + 1; j < n; j++)
        {
            if (abs(chinese[i] - chinese[j]) > 5) continue;
            if (abs(math[i] - math[j]) > 5) continue;
            if (abs(english[i] - english[j]) > 5) continue;
            if (abs(total[i] - total[j]) > 10) continue;

            ans++;
        }
    }

    cout << ans << endl;
    return 0;
}
```

几个写法上的选择：

- **`total[i]` 在输入时就累加好**，不要留到比较循环里重复算（每对算一次总分，等于白算 $O(n^2)$ 次加法）
- **`continue` 连写**，把"四个条件都满足才计数"翻译成"有一个不满足就跳过"，比一行超长 `&&` 好读也好改
- **`j = i + 1`**，直接消灭重复和自比

### 2.8 关键要点

- 局部数组**不会自动清零**，`int a[N];` 里是垃圾；写 `= {0}`
- 二维数组越界读**不一定崩**，会静默读到隔壁元素——比崩溃更难查
- "分差"必须 `abs()`，否则同一个事实会得出两个结论
- "多少对"类计数，用 `j = i + 1` 从源头去重，别用结果减补丁
- 能预计算的就预计算（总分在输入时算好），别在双层循环里重复算
- 四个独立判断用 `continue` 串起来，比一行巨长的 `&&` 更不容易写漏

### 三点收获

**1. 静默失败是这周真正的主线**

这周遇到五次"接口说成功、实际没做"：截图（DPI）、键盘注入（SendKeys）、切前台（前台锁）、记忆（模型自我否定）、好友申请（假 flag 返回链路可疑的好结果）。

它们有一个共同特征：**返回值/日志都正常**。

对策是同一个套路——**不要相信返回值，去验证副作用**：

- 截图不看"调用成功"，去量图片尺寸对不对
- 注入不看"发送成功"，去读回写入文件的内容
- 切前台不看"API 返回"，去看窗口句柄是不是真变成前台了
- 主动聊天不看"配置生效了"，去算 `next - last` 的分钟数

**这条可以推广成一句：能用可观测量证明的，就别用返回值证明。**

**2. 三个 bug 都是读源码定位的，不是猜的**

- 主动聊天为什么慢 → 读 `_proactive_loop`，看到 `sleep(900)` / `sleep(420)`
- 好友申请为什么收不到 → 读 `whitelist_check/stage.py`，看到 `stop_event()`
- 放行为什么安全 → 读 `internal.py`，看到 `skip llm request: empty message`

三个问题如果只在"配置改了吗""重启了吗"这个层面打转，永远找不到根因。**源码就是最完整的那份文档**，而且它不会撒谎。

**3. C++ 的 bug 和系统的 bug 是同一类**

P5728 的四个 bug 里，三个是"**没初始化**"和"**边界错了**"：数组没清零、下标越界、循环边界导致重复。

这和项目里的问题惊人地像：

| C++ | 系统 |
| --- | --- |
| 数组没初始化 → 读到垃圾 | 状态没重置 → 读到上次的残留 |
| 下标越界 → 静默读隔壁 | 参数越界 → 静默用了默认值 |
| 循环边界错 → 重复计数 | 重试逻辑错 → 重复执行 |

所以"检查初始化和边界"这个习惯，不是只对写算法有用。
