## 二、提示词数据集：从 700 KB 压缩包到一份拆解笔记

11-19 那天做了一件完全不同的事：把一个公开的提示词合集解包、建索引、查重、然后拆解其中一份。

### 2.1 规模

```
来源：togg53192-cmd/jailbreaks（GitHub）
压缩包：国内全部模型破甲.zip
解包后：54 个文件 / 20 个厂商分组 / 737,429 字节
```

按厂商分组：Alibaba、DeepSeek、Moonshot AI、Anthropic、Google、Meta、Mistral、OpenAI、xAI、Zhipu AI、Tencent、Xiaomi、Meituan、StepFun，外加几个社区分组（`0x8D jailbreaks`、`Stealth Models`、`DarkyHArry`、`modemnakata`、`raghavraut`）。

### 2.2 自己写了个索引脚本

文件一多，靠 `ls` 是没法用的。写了个 `_build_index.py`（只读扫描，不动原文件）自动生成 `INDEX.md`：

- 每个分组：文件数、总字节
- 每个文件：标题、大小、行数
- 编码兜底：`utf-8 → utf-8-sig → gbk → latin-1` 依次尝试（实测确实有 GBK 文件）

这一步的价值不在脚本本身，在于**它逼我把"有多少东西"量化出来**——54 个文件里，真正不同的文本有多少？于是就有了下一步。

### 2.3 查重：发现了三份"同文不同壳"

拿 sha256 一算，发现：

```
DeepSeek/deepseekv4.1 and v4.1-1017.md   sha256 764983203…   LF
Stealth Models/Unified.md                sha256 764983203…   LF    ← 逐字节相同
Stealth Models/Beam.md                   仅行尾为 CRLF（97 行 → 多 97 字节）
```

**三份"不同目标"共用一份内容。**

这里有个技术细节值得记：**按 hash 查重会漏掉 Beam**。因为 CRLF 让字节数变了 97 个，sha256 完全不同。正确做法是**先做行尾归一化，再算 hash**。

这条坑很典型：去重算法看着对，但只要输入有一点格式差异就失效。**内容相同的判定，不能只依赖一种指纹。**

### 2.4 拆解笔记：它是怎么工作的

从中挑了一份写拆解笔记（195 行）。结论先说：

> **这是一次"规则捕获"，不是一次说服。**

它的技术含量集中在一个点上：**把安全判定从"价值权衡"降级为"集合查表"**。

具体手法三层：

1. **冒充运行时配置**——把自己伪装成 harness 注入的 `<system-reminder>`，借用"系统消息"的权威感
2. **重写规则层级**——宣称"没有比本文档更严格的策略"，把自己抬到所有其它规则之上
3. **把拒绝预先定义为故障**——"misfire"而不是"选项"，于是拒绝变成需要解释的异常

一旦模型接受"只需比对六条边界"这个前提，后面所有请求就变成"未命中即放行"。

**我还写了一条元结论**：它自称权威，但**权威不能由内容自证**。判定的合法性来自"谁在什么通道加载了它"，不来自"它说自己排他"。

### 2.5 这件事的副产品

归档完反而看清了一件事：**54 个文件的信息量远小于 737 KB。**

去掉同文的三份、去掉纯格式差异的，真正不同的文本大概只有一半。这和刷题是同一个道理——**看上去很多，去重之后才看见骨架。**

## 三、补记：上期漏写的外设电量那一摊

上周日的周报是 12:13 发的，下午做的事没写进去。补一段，因为这是最近最硬的一次工程实践。

### 3.1 目标

做一个托盘小控件，显示鼠标 / 键盘的无线电量。

### 3.2 结果

| 设备 | 结果 |
| --- | --- |
| **AULA SC580SE 鼠标（蓝牙）** | ✅ 能读，`DEVPKEY_Bluetooth_Battery` 一行代码搞定（当时读到 2%，该充电了） |
| **AULA 鼠标（2.4G）** | ❌ 读不到 |
| **MCHOSE G87 V2 键盘（2.4G）** | ❌ 读不到，`WIRELESS_VID` 表里只能标"读不到" |

### 3.3 为什么 2.4G 读不到（证据）

不是偷懒，是硬件和系统层面就不给：

```
接收器接口：  mi_02 usage=FF31(厂商) 65B 命令通道
             mi_04 usage=FF70(厂商) 65B 命令通道
feature 报告： 报告 ID 0x00~0x40 全部返回空
标准 HID 字段：描述符里没有 Battery Strength（page 0x06 / usage 0x20）
输入报告：     HidD_GetInputReport 无数据；阻塞读取永不返回
```

**结论：2.4G 电量只在厂商私有通道里，Windows 不知道，也没有公开协议。**

### 3.4 途中还拆了 MCHOSE HUB（没拆动）

那个驱动软件是加固过的 Electron：

- 主进程编译成 **V8 字节码**（`index.jsc` 1.3 MB），不是 JS，Ghidra 也吃不下
- 界面从 CDN 加载，本地没有 HTML
- `--remote-debugging-port` 被 fuses 关掉
- 无障碍树关闭，UIA 只读到 1 个元素
- 配置文件里的 `batteryLevel` 是**静态值**（盯了 3 分钟、18 次采样零变化）

### 3.5 找到公开协议，但对不上

后来找到一份 [MCHOSE 协议规范](https://gitlab.com/unk9201422/Mchose/-/wikis/Protocol-Specification)（别人逆出来的），里面有 XOR 0xFF 编码、报告 0x11/0x12/0x13、电量在推送事件 0xE2 第 4 字节。

按它发 `0x0B 0xAA` 触发状态推送——**键盘 33 个报告 ID 全部无响应**。那份协议是给鼠标的，键盘是另一套。

### 3.6 顺手把控件重写成了 C#

既然 2.4G 读不到，就把能做的做扎实：PowerShell 版占 **99 MB**，实在谈不上"没影响"。

用系统自带的 `csc.exe`（不用装 .NET SDK）重写成 C#：

```
battery_tray.exe   12 KB
实测内存           33.7 MB（原来是 99 MB）
稳定性             30 秒内内存和句柄都不涨
```

**重写时抓到一个真 bug**：C# 版第一次读成 **83%**，因为去重时按"取较大值"处理，结果取了 8 月那套旧配对的残留。改成**按"最后出现时间"取最新**后，正确显示 2%。

### 3.7 这一摊教了我三件事

1. **"读不到"要先证明，再下结论。** 我一开始以为是代码问题，后来用"肯定在发数据的鼠标接口"做对照，才发现是自己的读取层有问题。
2. **安全机制不是 bug。** cookie 的 `v20` 加密是设计如此，不是能绕过的东西。
3. **工具会咬人。** 中途 USBPcap 因为 stdin 接了 NUL，无限循环问同一个问题，**一次写出 17.4 GB 日志**。清了两轮才清干净（磁盘空间全部要回来了）。

## 四、这周的三个规律

### 4.1 卡点是可以量化的

刷题时我习惯记"访问次数"，这周第一次把它当数据看：**访问 40 次以上的题，全部是"细节敏感型"**（高精度进位、字符串下标）。

这意味着：**下次遇到同类题，先别急着写，先把边界列出来。**

### 4.2 去重比收集难

54 个文件、737 KB，去重后信息量掉了一半。而且**按 hash 去重会漏**——CRLF 让同一份文本换了指纹。

正确顺序是：**归一化 → 再比。** 不只是文本，任何"看起来不一样但其实一样"的东西都适用。

### 4.3 冒充系统消息是最省力的攻击

那份拆解笔记里最值钱的一句：**权威不能由内容自证。**

判断一个指令该不该听，看的是"谁在什么通道给的"，不是"它说它最重要"。
